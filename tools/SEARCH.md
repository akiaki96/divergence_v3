# 探索（足立法）と，シミュレータでの再現

探索のソルバーは `external/micromouse_simulator/solver` の adachi を，シミュレータと同じソースのまま使う。
実機は壁を読むたびにログを1行残し，シミュレータはそのログを再生して，実機が何を見てどう判断したかを再現する。

## ファイル

| ファイル | 役割 | 編集 |
|---|---|---|
| `search_presets.json` | 探索のプリセット（速度・加速度・使うターンの集合・超信地旋回・壁の補正） | 手で |
| `gen_search_presets.py` | `config/search_presets.hpp` を生成する。スラロームが設計されていなければビルドを止める | — |
| `Core/Src/app/search.cpp` | 探索のループ（壁を読む → ソルバー → 動作を積む）とログ | — |
| `Core/Src/app/search_lookahead.cpp` | ソルバーの先読み（次に読む壁の8通りで先に回し，読んだら結果を取り出す） | — |
| `Core/Src/common/wall_sensor.cpp` | IRセンサーの位置の対応と壁の判定 | 対応がずれていたら |
| `Core/Src/common/wall_control.cpp` | 直進中の横壁による向きの補正 | — |
| `Core/Src/common/front_correction.cpp` | 前壁の距離による S90 の入口の補正（換算表は `ir_calibration.json` → `gen_front_distance.py`） | — |
| `front_correction.py` | 探索のログから前壁の補正（前後のずれ e，補正 δ，壁切れとの相関）を評価する | — |
| `Core/Inc/config/mouse_config.hpp` | `config::wall`（閾値・基準値・ゲイン），`config::search`（壁を読む位置・ゴール・ログの行数・電池） | 調整で |

プリセットの例（`search_presets.json`）：

```json
{
  "500": {"speed": 500, "accel": 3000, "straight_speed": 1000, "turns": ["S90", "L90", "T180"],
          "pivot": {"omega": 360, "alpha": 2500}, "wall_control": true, "note": ""}
}
```

- `turns` に使うターンの種類を並べ，`speed` でそれぞれのスラロームが決まる（例 `S90` と 500 → `config::slalom::S90_500`）。
  探索中でも既知区間では大回りなどを使うので，複数持てる。種類ごとに `SearchPreset` の集合へ入る：
  - `OrthoTurns`（区画に沿ったターン）… `S90`, `L90`, `T180`
  - `DiagonalTurns`（斜めのターン）… `IN45`, `OUT45`, `V90`, `IN135`, `OUT135`。1つでも並べたときだけ作る
- `S90` は必須（未知区間は区画境界で1歩ずつ進むので，入口・出口とも区画境界の小回り90°で曲がる）。
  並べていない種類は `nullptr` で，使わない
- `slalom_params.json` にその速度の設計がないとビルドが止まる（設計済みの速度が表示される）
- `straight_speed` は既知の区画が続く直進で加速する最高速度 [mm/s]（下の節）。省略すると `speed`（加速しない）。
  加速・減速は `accel`
- `slalom` は使うスラロームの組（`slalom_params.json` の速度のキー，`SLALOM.md` の「スラロームの組」）。省略すると
  `speed` と `fan` から決まる（`"500"` / `"500_fan"`）。組の速度は `speed` と同じでなければならない（ターンは探索速度で曲がる）。
  `turns` に並べたターンはすべてその組に保存されていること（組 `b` を小回り90°だけ作ったなら `"turns": ["S90"]`）
- `pivot` は超信地旋回（行き止まりの180°）の最大角速度 [dps] と角加速度 [dps/s]
- `fan` を `true` にするとファンを `config::fan::RUN_DUTY` で回して走り，ターンもファンONの設計（`"500_fan"`，
  `config::slalom::S90_500_FAN`）を使う。省略すると `false`
- `wall_control` は**実験中**の横壁による向きの補正。省略すると `false`
- `front_correction` は**実験中**の前壁の距離による S90 の入口の補正（下の節）。省略すると `false`
- `goal` はゴール区画 `[x, y]`。省略すると `config::search::GOAL_X/Y`（既定 (7,7)）。
  試験用プリセット `500_goal10`（`Test` → `Search`）は `"goal": [1, 0]` で，スタート (0,0) から隣の (1,0) へ行って戻る。
  スタート区画の東は壁とみなす（規定）ので，経路は (0,0) → (0,1) → (1,1) → (1,0) → 戻りは逆順になり，
  短い距離で右左折・行き止まりでの超信地旋回・帰り探索・迷路の保存（ゴール (1,0) として記録）を一通り試せる
- `one_way` を `true` にすると片道（足立法でゴールへ行き，ゴール区画の中央で止まる）。省略すると `false`＝往復
  （ゴールの後もスタートへ戻る探索を続け，スタート区画の中央で止まる）。片道で保存した迷路は complete にしない
- `reset_walls` を `false` にすると，始めに壁を消さず，保存した最新の迷路（`maze_store`，Fast と同じもの）の壁と
  通った区画を引き継いで探索する。保存した迷路がなければ空の迷路から始める。省略すると `true`＝壁を消す。
  既定（`500` など）は壁を消す往復，変則の `500_oneway` は壁を引き継ぐ片道（続きの探索を足したいとき）
- `confirm` に最短走行のプリセット名（`run_presets.json` のキー）を書くと，最短走行の経路で確かめる探索になる
  （下の節）。`500_confirm` は `"confirm": "1200_dia"`。`one_way` とは一緒に使えない（生成がエラーで止まる）
- `menu` は並べるメニュー。省略（`"search"`）で `Run` → `Search`，`"test"` で `Test` → `Search` に並ぶ。
  `Test` → `Search` の `500_goal01` は `"goal": [0, 1]` で，最初の半区画で (0,1) に入って壁を読んだ時点で
  ゴールとなり，(0,1) の中央で止まって超信地旋回し，(0,0) へ戻って止まる（最初の加速・壁読み・旋回・停止だけを試す）
- 壁を読む位置はプリセットによらないので `config::search::READ_LEAD_MM` にある
- プリセットはメニュー `Run` → `Search`（`"menu": "test"` のものは `Test` → `Search`）に，JSONに書いた順で並ぶ
  （それぞれ `config::menu::MAX_CHILDREN` 個まで）

## 走らせるまで

1. **壁センサーの確認**：メニュー `Device` → `IR` → `Wall check`
   - シリアルに機体の位置ごとの値（`L FL FR R`），前左・前右それぞれの判定，壁の判定，元の変数の値が出る。
     LEDバーは左から左・前左・前右・右の壁の判定
   - **各センサーを手でふさいで，位置の対応が合っているか確かめる**。対応は `wall_sensor.cpp` の `pick()` に
     ある（ずれていたらここだけ直す）。今は変数名どおり 左 = `irL`，前左 = `irFL`，前右 = `irFR`，右 = `irR`。
     前・横の区別は前壁スイープで実測済み，横の左右は確認済み。前の左右（`irFL`/`irFR`）だけここで確かめる
   - 区画境界の `READ_LEAD_MM` 手前（探索で壁を読む位置）に置き，壁があるとき・ないときの値の中間を
     `config::wall::THRESH_*` に，区画の中心線上で両側に壁があるときの左右の値を `REF_*` にする
   - **前壁の閾値は `Device` → `IR` → `Front check` で決める**。前壁は前左・前右のどちらかが自分の閾値
     （`THRESH_FRONT_LEFT` / `THRESH_FRONT_RIGHT`）を超えたら壁あり（同じ値なら「大きい方の値 > 閾値」）。
     後端を後壁に当てて置き，`wall`（次の区画の向こう側に前壁）と `no wall`（その壁を外す。さらに1区画先に
     壁を置くと遠い壁の場面も測れる）を，左右の位置や向きを少し変えて何回か走らせる。機体が壁を読む位置まで
     進んで止まり，前左・前右を500回読む。`show` に前左・前右ごとの壁ありの最小・壁なしの最大と閾値の候補，
     今の閾値での読み落とし・読みすぎの回数が出る（`reset` で消す）
   - 抜けるときはリセット
2. **探索**：機体の後端をスタート区画 (0,0) の後壁に当てて北へ向け，`Run` → `Search` → プリセットを選ぶ
   - ゴール（プリセットの `goal`，省略時は `config::search::GOAL_X/Y` = (7,7)）に着くとスタートへ戻る探索を続け，
     スタート区画の中央で止まる
   - 次のときは止まって，LEDバーが左右交互に点滅する（理由はシリアルに出る）：
     - `wall ahead` … 壁のある向きへ進もうとした（壁の誤読）
     - `segment rejected` … 区間を積めなかった
     - `profile error` … PlanProfileが区間を落とした，または壁を読む前に止まった
     - `too many steps` … ログの行数（`MAX_STEPS`）を超えた
     - `plan mismatch` … 加速して積んだ区間の途中で，ソルバーが直進以外を返した（起きないはず）
3. **ログの受け取り**：止まったら機体を持ち上げて置く（`haltByAccZ`）と，`tools/main.py` が2つ保存する
   - `tools/log/search/<preset>.csv` … 壁を読むたびに1行（位置・壁・ソルバーの動作・帰り探索中か・IRの値，
     読んだときの並進の目標位置 `pos_target` と実測 `pos_measured` [mm]。差が追従遅れ。
     `prepare_us` はその壁を読む前に8通りでソルバーを回した時間，`take_us` は読んでから結果を取り出すまでの時間 [us]。
     `left/front/right` はソルバーに渡した壁，`sensor_left/front/right` はセンサーの壁，`known` は地図の壁を使ったか，
     `rechecked` は止まって読み直した後の読みか，`run_cells` はその読みで加速して積んだ直進の区画数）
   - `tools/log/search/<preset>_trace.csv` … 走行中の目標・実測の位置と角度，壁の補正（68s分を間引いて記録，約22Hz）

## スラロームと直進の組み合わせを試す（試験用プリセット）

1つのプリセットが「スラロームの組（`slalom`）＋ 既知の直進の速度・加速度（`straight_speed` / `accel`）」の組み合わせになる。
名前を付けて `"menu": "test"` で並べれば，`Test` → `Search` から選んで続けて試せる。ログはプリセット名のファイル
（`tools/log/search/<preset>.csv` など）に分かれるので，組み合わせごとの結果がそのまま残る。

```json
"500_s1000":  {"speed": 500, "accel": 3000, "straight_speed": 1000, "slalom": "500",   "turns": ["S90", "L90", "T180"], ..., "menu": "test"},
"500b_s1000": {"speed": 500, "accel": 3000, "straight_speed": 1000, "slalom": "500_b", "turns": ["S90"], ..., "menu": "test"}
```

- 今ある試験用：`500_s800` / `500_s1000` / `500_s1100`（組 `500`），`700_s1100`（組 `700`）。どれもゴール (1, 0)（`"goal": [1, 0]`）
- 1つのメニューに並ぶのは `config::menu::MAX_CHILDREN`（10）個まで（超えるとビルドが止まる）
- `straight_speed` の上限は，最高速度から読んだ区画の中央より手前で止まれること（`BRAKE_DECEL` 8000 なら約 1130 mm/s）。
  超えるとビルドが `a search preset cannot run` で止まる
- 探索の始めのシリアルの1行目に，プリセット名・速度・既知の直進の速度・小回り90°の定数名（`S90_500_B` なら組 `b`）が出る

## 既知の区画の直進を加速する（`straight_speed`）

- 次に入る区画の左・前・右の壁がすべて分かっていれば，読んでも地図は変わらないので，その区画でのソルバーの
  答えは決まっている。先読み（`search_lookahead::prepare` の chains）が，そういう区画が続く間ソルバーを既知の壁で
  進めて，直進が何区画続くかを数える
- 壁を読んで動作が直進なら，その区画数を1本の台形（`speed` → `straight_speed` → `speed`，加速度 `accel`）で積む。
  区間の途中の境界でも壁は読むが，動作は積まない。区間の終わりは `speed` なので，続く小回り90°・未知の区画は今までどおり
- 数える時間は次の壁を読むまでの `CHAIN_BUDGET_RATIO`（4割）まで。超えたら数えるのをやめる（区間が短くなるだけ）
- 3辺とも既知の区画では，探索はセンサーではなく地図の壁をソルバーに渡す（センサーの壁はログに残る）

### 壁が地図と食い違ったとき

3辺とも既知の区画で，読んだ壁が地図と違ったら：

1. 減速して止まる（加速区間の途中なら残りを取り消して `config::search::BRAKE_DECEL` で。`PlanProfile::brake`）
2. 1つ手前の区画の中央（読む境界の半区画手前）まで下がる（`BACK_SPEED` / `BACK_ACCEL`。横壁の制御と壁切れの検出は止める）
3. 止まっている間に先読みを8通りで作り直し，中央から `speed` まで加速して同じ境界へ向かう
4. 同じ読む位置で壁を読み直し，その値をソルバーに渡す。地図と同じなら最初の読み違いだったことになり，
   違えば地図がその値に書き換わり（`search_step` の `set_wall`），経路もそれに従う

食い違いの回数・地図を書き換えた回数・それぞれの区画と壁は，終わりにシリアルへ出る（`mismatch step …`）。
`straight_speed` は，そこから読んだ区画の中央より手前で止まれる速さまで（ビルド時に検査）。

## 最短走行の経路で確かめる探索（`confirm`，`500_confirm`）

往復の探索（足立法でゴールへ行き，未探索を優先してスタートへ戻る）は，最短走行が通る区間の壁を読み残すことがある。
`confirm` のプリセットは，ゴールに着いてから最短走行の経路生成（`time_based_dijkstra`，コストは `confirm` の
最短走行のプリセットから `fast_plan::applySolverCosts`）で経路を確かめてから戻る
（ソルバーは `adachi::SearchKind::to_goal_fast_confirm_back`，シミュレータでは `adachi_fast_confirm`）：

1. ゴールに着いたら「確認」を予約する。確認では，未知の壁を通れるとみなした地図（`wallzero`，楽観的な壁）で
   最短走行の経路を求め，その経路が通る区画どうしの間の未知の壁を「確かめる壁」にする（経路が横切る壁はすべてここに入る）
2. 確かめる壁の隣の区画へ足立法（歩数）で順に行って読む。確かめる壁のどれかが有る（経路が崩れた）と分かるか，
   すべて分かったら，また確認を予約する
3. 確かめる壁がなければ，壁とみなした地図（`wallone`，最短走行が実際に使う地図）でも解き，時間が一致すれば
   確定してスタートへ戻る。延びる（2×2 のゴール領域で，別のゴール区画への到達が遅くなる）ときは，領域の区画と，
   区画ごとの楽観的な経路の未知の壁を確かめる壁にして続ける

予約した確認は，止まりやすい歩まで先送りする：直進で入った区画から直進で出る歩（安定した直線の途中。ターンの直後は
選ばない）か，行き止まり（どのみち区画の中央で止まって旋回する）。ゴール領域の区画では確認しない（ゴールした直後には
止まらない）。予約している間は，確かめる壁が残っていればそこへ，なければスタートへ未探索の区画を優先して進む。
予約から8歩たっても来なければ直進ならどこでも，24歩でどの歩でも確認し，スタートに着いたら必ず確認する。

経路計算は重い（楽観的な地図ではキューが最も長くなる）ので毎歩はしない。確認の歩ではソルバーは壁を記録する
だけで動作を返さず（`adachi::search_check_pending()`），機体は読んだ区画の中央まで減速して止まり，止まったまま
`adachi::search_check()` で経路を求めてから，その場から次の1歩を積む（直進は半区画，左右は超信地旋回90°の後に
半区画，行き止まりは180°の後に半区画）。止まって書く設定（`maze_save::WHILE_RUNNING = false`）なら止まったついでに
迷路も書く。そのほかの歩は今までどおり（先読み・既知の直進の加速）

- シミュレータでの比較（大会の迷路 61 個とランダムな迷路 40 個，2026-10-10）：歩数は `adachi_return` 148.9 →
  227.4（`adachi_shortest` 217.0），探索後の最短走行の推定は 10560 → 9534 ms（`adachi_shortest` 9512 ms）。
  確認（止まる回数）は平均 9.7 回・最大 29 回（予約したその場で止まると 16.7 回・最大 43 回）。大会の迷路で
  止まった歩は直線の途中 53%，行き止まり 37%，予約から8歩の直進 10%，予約から平均 2.2 歩後。
  ホストでの確認1回の計算は平均 0.2 ms・最大 1.4 ms
- 探索の終わりのシリアルに `fast-run confirm: N checks (path fixed), compute max … us, mean … us, queue peak …;
  last: 楽観 / 悲観 ms, 確かめる壁の数` が出る。`compute` が実機での確認1回の計算時間（止まっている間）
- 壁読みのログ（`search/<preset>`）の `check` 列が1の行が確認の歩で，`check_targets`（確かめる壁の数），
  `check_ms`（楽観的な経路の推定時間），`check_us`（計算時間）。`action` は確認の後の1手
- シミュレータで再生するときは `--solver adachi_fast_confirm` を指定する（コストは既定値なので，`confirm` の
  プリセットのコストと違うと経路が変わることがある）
- ホスト試験：`tools/host_test/run.sh` の `test_search_confirm`（実機の流れ：先読み＋確認の歩で止まって
  `search_check` が，シミュレータのソルバーと毎歩一致する）

## 前壁の距離による S90 の入口の補正（[実験中]，`common/front_correction.hpp`）

S90 が続くと，前のターンの出口のずれ（新しい向きの前後）が次の S90 の入口に入って積み重なる。壁を読む位置
（境界の `READ_LEAD_MM` 手前）では前のセンサーが新しい向きの前壁（約 184 mm 先）を見ているので，S90 を積むときに
前壁があれば，前左・前右の値を換算表（`tools/ir_calibration.json` → 生成ヘッダ `config/front_distance_table.hpp`）で
距離にし，基準 `REF_*` とのずれ e（正：機体は実際は後ろ）から入口オフセット（pre-offset）を伸び縮みさせる。

- 補正 δ = clamp(GAIN·(|e| − DEADBAND)·sign(e), ±MAX)（`config::front_correction`，初期値 0.5 / 10 mm / 15 mm）。
  pre が 0 を下回る分（機体が前に出すぎ）は実測位置をずらして（`Odometry::requestShiftX`）位置制御で戻す
- 補正するのはプリセットの `"front_correction": true` だけ（今は `500_fc` と，ゴール (1,0) の短いコース `500_fc_goal10`。それぞれ `500`・`500_goal10` と同じ条件で比べる）。
  しないプリセットでも e はログの `front_err` 列に残る（`front_corr` は補正した δ，しないプリセットでは 0）
- 既存のログ（2026-10-05）：e の σ は約 15 mm（壁切れで位置が合っている直進の後でも同じ）で，次の壁切れの
  ずれとの相関はほぼ 0（n 36, r −0.08）。1回読むだけだとノイズ（壁板の反射率・向き・横ずれ）が大きいので，
  不感帯で大きなずれだけを小さくする

手順：
1. `Device` → `IR` → `Front check` → `wall` を置き方を変えて何回か走らせ，結果の
   `front wall distance (mean, table)` を見る（静止での `REF_*` の候補。走行中の値は少しずれる）
2. `Run` → `Search` → `500` と `500_fc` を同じ迷路で走らせる（S90 が続く区間を入れる）
3. 評価：`python3 tools/front_correction.py tools/log/search/500_fc.csv --edges tools/log/search/500_fc_edges.csv --rows`。
   直前の動作ごとの e の分布，補正がかかった読み，次の壁切れのずれとの相関（効くなら負）を出す。
   `--suggest-ref` で直進の後の読みの中央値（走行中の `REF_*` の候補），`--ref FL FR` で REF を試せる

## 迷路の保存（`app/maze_store.hpp`，`device/flash_bank.hpp`）

ゴールに着いた後は走りながら迷路をフラッシュに追記し，スタートまで戻って終わる（`finished`）と「探索し終えた」
（complete）記録を追記する。途中で止まっても，ゴールの後に保存した最後の迷路（partial）で最短走行できる
（最短走行は未知の壁を壁とみなす）。止まった歩の後の迷路は壁の誤読があり得るので保存しない。

- 保存先はフラッシュの最後の2セクタ（A面 = セクタ10 `0x080C0000`，B面 = セクタ11 `0x080E0000`，各128KB）。
  プログラムが重ならないように，`STM32F405XX_FLASH.ld` の FLASH 領域は 768KB にしてある
- 1面を記録（180byte）の大きさの枠に区切り，先頭から順に追記する（1面 728枠）。記録：ソルバーの `wallzero`
  （未知を壁なし）と `wallone`（未知を壁あり）の2枚，通った区画，ゴール，探索し終えたか，sequence（+1ずつ），CRC32。
  読むときは正しい記録のうち sequence が最大のもの（各面の最後の正しい枠を比べる）。以前の形式（面の先頭に1件）もそのまま読める
- 消去（1面 1〜2s，CPU が止まる）は探索を始めるとき（IMU 校正の前，LED バー全点灯）だけ。最新の記録がある面に
  `config::maze_save::RESERVE_SLOTS`（160）枠の空きがあればその続きに書き，なければもう一方の面を使う（空きがなければ消す）。
  最新の記録がある面は消さないので，消している途中で電源が落ちても最新の記録は残る
- 走行中の書き込み（`config::maze_save::WHILE_RUNNING = true`）：ゴールに着いた歩で1回，その後
  `EVERY_STEPS`（4）歩ごとに，迷路が前の保存から変わっていれば積み，次の壁を読むまでの待ちのループで1語（32bit）ずつ書く。
  フラッシュに書いている間は CPU がフラッシュから命令を読めず止まるが，1語なら典型 16us・最大 100us
  （データシートの tPROG）なので，1kHz の制御の割り込みはその分遅れるだけで落ちない。1件 45語で約 1ms，1区画の走行（100ms 以上）に十分収まる。
  CRC の語を最後に書くので，書きかけの記録は無視される
- `WHILE_RUNNING = false`：保存する歩が直進か行き止まりなら区画中央で止まって書き（1語ずつ），そこから加速し直す。ターンの歩なら次の機会に回す
- ログ：探索の終わりに `maze save: ...; N records (failed, unchanged, refused), word max X us, control gap max Y us`。
  `word max` は1語の書き込みで CPU が止まった最大，`control gap max` は制御の割り込みの間隔の最大（名目 1000us）。
  探索ログの `saved` 列はその歩で保存を始めたか
- メニュー `Run` → `Maze` → `Show`：両面の使用枠・最後の記録と最新の迷路をシリアルに出す（`---`/`|` 壁，` ? `/`:` 未知，
  `S` スタート，`G` ゴール，`.` 通った区画）。`Clear`：両面を消す
- ソルバーへ戻すのは `maze_store::applyToSolver()`（アルゴリズムの `*_init()` の後に呼ぶ。最短走行で使う）
- ホスト試験：`tools/host_test/run.sh` の `test_maze_store`（フラッシュは RAM の偽物。書きかけでの停電，面の切り替えを含む）

## シミュレータで再現する

`external/micromouse_simulator` で（環境の準備はその readme を参照）：

```bash
# ログを再生する。位置・判断がずれた歩があれば一覧を出して終了コード1
python run_headless.py --replay ../../tools/log/search/500.csv

# 走らせた迷路の画像を渡すと，壁の誤読（どの区画のどの壁を，どのIR値で読み違えたか）も出す
python run_headless.py --replay ../../tools/log/search/500.csv --maze-image maze_image/<迷路>.png

# ブラウザで再生する（誤読した壁はオレンジの破線）
python main.py --replay ../../tools/log/search/500.csv --maze-image maze_image/<迷路>.png
```

- 壁の誤読が出たら，その行の `ir_*` と `config::wall::THRESH_*` を見比べて閾値を直す
- 判断の不一致が出たら，実機とシミュレータでソルバーのコードか設定（ゴール・帰り探索）が違う。
  サブモジュールのコミットがそろっているか確かめる
- 一度位置がずれると以降の行はすべて不一致になるので，最初の不一致から見る

## 注意

- **実機では未確認**。閾値・基準値・ゲイン（`config::wall`）は仮の値なので，まず `Wall check` で決める
- 横壁の補正は直進中（目標の角速度が0で，並進が `MIN_VELOCITY` より速い間）だけ効く。
  補正した角度は旋回の後も残る（旋回は相対角度で積むため）
- 機体の実測の位置（エンコーダ）が区画境界の `READ_LEAD_MM` 手前に来たら壁を読み，その間に次の動作を積む
  （目標位置で待つと，追従遅れのぶん実際より先で読んだことになる）
- ソルバーは先読みする（`app/search_lookahead.hpp`）。動作を積んだ直後に，次の区画で読む左・前・右の壁の
  8通りすべてでソルバーを回して結果の状態を取っておき（`adachi::search_save/search_restore`），壁を読んだら
  合う結果を戻すだけにする。ソルバーの計算は1歩を走る間（500mm/sで約300ms）に移るので，`READ_LEAD_MM` の
  短さ（500mm/sで10mmなら20ms）には縛られない。8通りの計算が1歩の走行時間より長いと，読む位置で待たずに
  遅れて読むことになる（ログの `prepare_us` で確かめる）
- 探索のログは CCMRAM に置いている（スタートアップは CCMRAM を0にしないので，件数だけで有効な範囲を表す）
